# THE OS

Assistant-first Windows environment centered on **LYRA**.

## Current vertical slices

The repository currently proves ninety-three boundaries:

1. **Verified Windows action** — deterministic intent -> `ActionRegistry` -> Windows adapter -> process verification.
2. **Persistent LYRA memory** — explicit remember/recall intents backed by local SQLite.
3. **Provider-neutral AI conversation** — unmatched conversation can fall through to a configured AI provider.
4. **Bounded session context + planner routing** — visible user/LYRA turns are kept in memory for the current process.
5. **AI tool planning with local authority** — the model may propose only tools advertised by THE OS; THE OS validates the proposal, converts it to a registered `ActionRequest`, executes locally, and reports verified results.
6. **Verified multi-step tool loop** — after each successful local action, THE OS returns the verified result to the model so it can continue the same request with the next required action. The loop is capped at four local actions and stops immediately on failure.
7. **Local risk policy + confirmation gate** — action risk is resolved by THE OS, not by the model. `READ_ONLY` and `NORMAL` actions may proceed automatically; `CONFIRM`, `DESTRUCTIVE`, and `PRIVILEGED` actions pause before side effects and require explicit user approval.
8. **Cooperative task control** — conversational/tool tasks expose Pause, Resume, and Cancel controls. Pause blocks at safe execution checkpoints; Cancel prevents later local side effects and provider continuations after the next checkpoint.
9. **Bounded file/folder actions** — LYRA can inspect local path metadata, search names inside a user-specified root, and ask Windows to open an existing file or folder. Files with potentially executable/script suffixes are locally upgraded to `CONFIRM`.
10. **Controlled text-file reading** — LYRA can read at most 16 KiB from a local text file after explicit user confirmation. Binary-looking files are rejected; sensitive credential/key filenames are locally upgraded to `PRIVILEGED`.
11. **Previewed text-file mutation** — LYRA can create or fully replace a text file of at most 16 KiB only after THE OS prepares a local preview/diff and the user explicitly approves it. Existing files are `DESTRUCTIVE`; sensitive or executable/script-like paths are `PRIVILEGED`.
12. **Controlled path mutation** — LYRA can create one directory, move/rename a path without overwriting the destination, and send a path to the Windows Recycle Bin. Every mutation uses a local preview plus explicit approval; move/trash operations are `DESTRUCTIVE`, sensitive locations are `PRIVILEGED`, and protected Windows system paths cannot be moved or trashed.
13. **Bounded verified copy** — LYRA can copy a file or a directory tree while preserving the source. Copy is locally bounded to 256 entries and 64 MiB, refuses links/junctions and existing destinations, previews counts/size before approval, and verifies a content manifest before publishing the destination.
14. **Read-only system status** — LYRA can collect a bounded snapshot of current CPU, memory, system-disk, and battery state through a local Windows adapter. The action is read-only, performs no process enumeration, and does not mutate system configuration.
15. **Controlled process inspection** — LYRA can enumerate a bounded view of running processes after explicit confirmation. Only process name, PID, and resident memory are returned, capped at 12 entries; executable paths, command lines, usernames, and open files are excluded.
16. **Verified process termination** — LYRA can terminate one ordinary process by an exact PID only after a destructive local preview and explicit approval. The process identity is guarded by PID, name, and creation time; protected Windows processes and LYRA's own process are blocked, and exit is verified.
17. **Controlled visible-window inspection** — LYRA can enumerate a bounded view of visible top-level desktop windows only after explicit confirmation. At most 12 entries are returned with window title, process name, PID, and a process-local opaque target token. For a specifically requested window, an optional bounded literal query may filter title/process-name matches locally before the 12-result cap; hidden-window titles, screenshots, keystrokes, executable paths, raw window handles, and window contents remain excluded.
18. **Verified visible-window activation** — LYRA can bring one already-known visible top-level window to the foreground using the exact PID, bounded title, and opaque `target_token` returned by `window_snapshot`. Missing or non-unique opaque targets are blocked, minimized targets may be restored, and foreground state is verified locally.
19. **Confirmed graceful window close** — LYRA can request normal closure of one already-known visible top-level window by exact PID, bounded title, and opaque `target_token`. The destructive preview and execution guard bind all three values, the target is re-resolved exactly after approval, LYRA's own window remains blocked, the process is never force-killed, and disappearance of that exact window is verified.
20. **Verified visible-window minimization** — LYRA can minimize one already-known visible top-level window using exact PID, bounded title, and opaque `target_token`. The action remains normal, blocks LYRA's own window, changes no file or process state, and verifies locally that the exact token-matched window entered the minimized state.
21. **Verified visible-window maximization** — LYRA can maximize one already-known visible top-level window using exact PID, bounded title, and opaque `target_token`. The action remains normal, blocks LYRA's own window, and verifies locally that the exact token-matched window entered the maximized state.
22. **Verified visible-window restore** — LYRA can return one already-known visible top-level window from minimized or maximized state to normal size using exact PID, bounded title, and opaque `target_token`. The action remains normal, blocks LYRA's own window, and verifies that the exact token-matched target is neither minimized nor maximized before reporting success.
23. **Confirmed bounded foreground text input** — LYRA can submit at most 512 Unicode characters to one exact visible foreground window after a local preview and explicit confirmation. The target is bound to PID, bounded title, and the opaque token from `window_snapshot`; Enter, Tab, shortcuts, special keys, control characters, clipboard use, and typing into LYRA itself are blocked. THE OS verifies SendInput event submission and that the same target remains foreground, but does not inspect the application's content to claim that the text landed in a particular control.
24. **Confirmed bounded foreground key input** — LYRA can press only a fixed local allowlist of single keys on one exact visible window after a local preview and explicit confirmation. The approved PID, bounded title, target token, and key are execution-guarded; the target is reactivated after the confirmation dialog and foreground is verified before and after SendInput. Arbitrary modifier combinations, arbitrary virtual-key codes, clipboard operations, and implicit content inspection remain blocked.
25. **Deterministic natural application-name normalization** — `open_application` accepts a small bounded set of Portuguese leading articles (`a`, `o`, `um`, `uma`) before an application name, so phrases such as `um bloco de notas` resolve through the same local application registry as `bloco de notas`. The same normalization is applied before local risk classification, so wrappers cannot downgrade confirmation requirements for shells or administrative tools. No fuzzy matching or model-provided executable path is introduced.
26. **Verified Windows Calculator application alias** — `open_application` recognizes the deterministic local aliases `calculadora`, `calculator`, and `calc`, launches the Windows `calc.exe` target, and verifies either the launcher process or known Calculator runtime process names (`CalculatorApp.exe` / `Calculator.exe`). The alias remains a normal application action; no WindowsApps enumeration, fuzzy matching, shell command construction, or arbitrary executable path is introduced.
27. **Confirmed bounded foreground navigation-key input** — `press_key` accepts only `ENTER`, `ESCAPE`, `TAB`, `UP`, `DOWN`, `LEFT`, `RIGHT`, `HOME`, `END`, `PAGE_UP`, and `PAGE_DOWN` for one exact visible target selected by PID, bounded title, and the opaque target token returned by `window_snapshot`. Every key remains confirmation-gated and guarded by PID/title/token/key; after approval the exact token-matched target is reactivated and foreground is verified before and after a single virtual-key down/up pair. `press_key` itself never accepts modifiers or shortcuts; arbitrary virtual-key codes, clipboard use, raw window handles, and semantic content inspection remain blocked.
28. **Exact-window bounded foreground text input** — `type_text` requires the same opaque `target_token` returned by `window_snapshot` in addition to PID and bounded title. The local preview and execution guard bind PID/title/token/text hash, execution re-resolves exactly one token-matched visible window before Unicode `SendInput`, and raw window handles remain local.
29. **Exact-window verified activation** — `activate_window` requires PID, bounded title, and the opaque `target_token` from `window_snapshot`. The Windows adapter re-enumerates visible windows and activates only the unique token-matched target, eliminating same-PID/same-title ambiguity without exposing raw window handles.
30. **Filtered visible-window discovery** — `window_snapshot` accepts an optional bounded literal `query` when a specific window is being sought. THE OS still requires the privacy confirmation, enumerates visible titled windows locally, applies a case-insensitive substring match only against the bounded title or process name, and then applies the existing 12-result output cap. Regex, fuzzy matching, hidden-window inspection, and broader provider disclosure are not introduced.
31. **Exact-window graceful close** — `close_window` now requires the opaque `target_token` from `window_snapshot` alongside PID and bounded title. The local destructive preview carries a PID/title/token execution guard, execution re-enumerates visible windows and accepts only the unique token-matched target, then sends only `WM_SYSCOMMAND/SC_CLOSE` and verifies that the original exact window was destroyed or became non-visible; raw HWND values remain local and force-kill is still not used.
32. **Exact-window verified minimization** — `minimize_window` now requires the opaque `target_token` from `window_snapshot` alongside PID and bounded title. THE OS re-enumerates visible windows, accepts only the unique token-matched target, applies `SW_MINIMIZE`, and verifies `IsIconic` on that exact local HWND without exposing the handle or adding a confirmation gate to this normal window-state action.
33. **Exact-window verified maximization** — `maximize_window` now requires the opaque `target_token` from `window_snapshot` alongside PID and bounded title. THE OS re-enumerates visible windows, accepts only the unique token-matched target, applies `SW_MAXIMIZE`, and verifies `IsZoomed` on that exact local HWND without exposing the handle or adding a confirmation gate to this normal window-state action.
34. **Exact-window verified restore** — `restore_window` now requires the opaque `target_token` from `window_snapshot` alongside PID and bounded title. THE OS re-enumerates visible windows, accepts only the unique token-matched target, applies `SW_RESTORE` when needed, and verifies that `IsIconic` and `IsZoomed` are both false for that exact local HWND without exposing the handle or adding a confirmation gate to this normal window-state action.
35. **Confirmed exact-window directional navigation keys** — `press_key` extends its local allowlist with `UP`, `DOWN`, `LEFT`, and `RIGHT` while retaining `ENTER`, `ESCAPE`, and `TAB`. Each key is still confirmation-gated, bound to the approved PID/title/target-token/key guard, sent as exactly one virtual-key down/up pair, and verified only by SendInput event count plus exact-window foreground continuity; modifiers, shortcuts, arbitrary key codes, clipboard use, and semantic UI inspection remain blocked.
36. **Confirmed exact-window boundary/page navigation keys** — `press_key` extends its local allowlist with `HOME`, `END`, `PAGE_UP`, and `PAGE_DOWN` without introducing editing keys, modifiers, shortcuts, or arbitrary virtual-key codes. The exact PID/title/target-token/key guard, confirmation gate, single virtual-key down/up pair, and foreground verification remain unchanged; semantic UI effects are still not inspected or claimed.
37. **Destructive exact-window editing keys** — `press_key` extends the local allowlist with `BACKSPACE` and `DELETE`, but THE OS resolves those two keys as `DESTRUCTIVE` while navigation/control keys remain `CONFIRM`. The local preview warns that focused content may be removed, approval remains bound to PID/title/target-token/key, execution sends exactly one virtual-key down/up pair, and success verifies only SendInput acceptance plus exact-window foreground continuity rather than claiming what content was deleted.
38. **Confirmed exact-window select-all shortcut** — the separate `press_shortcut` tool accepts only `CTRL_A` (Ctrl+A) for one exact visible target identified by PID, bounded title, and the opaque target token from `window_snapshot`. Approval is bound to PID/title/token/shortcut, execution emits the fixed four-event sequence Ctrl-down, A-down, A-up, Ctrl-up, and THE OS verifies SendInput acceptance plus foreground continuity without reading application content. No other shortcut, arbitrary modifier combination, clipboard access, or semantic selection claim is introduced.
39. **Confirmed exact-window copy shortcut** — `press_shortcut` extends its local allowlist with `CTRL_C` (Ctrl+C) while keeping `CTRL_A`. The exact PID/title/target-token/shortcut guard and confirmation gate remain unchanged; execution emits Ctrl-down, C-down, C-up, Ctrl-up and verifies only SendInput acceptance plus foreground continuity. The preview warns that Ctrl+C may replace the current clipboard contents, but THE OS never reads clipboard data and does not claim that the application actually copied anything. Unlisted shortcuts and arbitrary combinations remain blocked.
40. **Destructive exact-window cut shortcut** — `press_shortcut` extends the local allowlist with `CTRL_X` (Ctrl+X), but resolves that shortcut as `DESTRUCTIVE` while `CTRL_A` and `CTRL_C` remain `CONFIRM`. Approval stays bound to the exact PID/title/target-token/shortcut; execution emits Ctrl-down, X-down, X-up, Ctrl-up and verifies only SendInput acceptance plus foreground continuity. The preview warns that focused content may be removed and the clipboard may be replaced. THE OS does not read clipboard data or inspect application content to claim what was cut. Unlisted shortcuts and arbitrary combinations remain blocked.
41. **Privileged exact-window paste shortcut** — `press_shortcut` extends the local allowlist with `CTRL_V` (Ctrl+V) and resolves it as `PRIVILEGED` because the clipboard may contain sensitive data that THE OS intentionally does not inspect before the target application consumes it. Approval remains bound to PID/title/target-token/shortcut; execution emits Ctrl-down, V-down, V-up, Ctrl-up and verifies only SendInput acceptance plus foreground continuity. THE OS does not call clipboard APIs, expose clipboard contents to the AI provider, or claim what was pasted. Other shortcuts remain blocked.
42. **Destructive exact-window undo shortcut** — `press_shortcut` extends the local allowlist with `CTRL_Z` (Ctrl+Z) and resolves it as `DESTRUCTIVE` because undo can alter, remove, or restore focused application content. Approval remains bound to the exact PID/title/target-token/shortcut; execution emits Ctrl-down, Z-down, Z-up, Ctrl-up and verifies only SendInput acceptance plus foreground continuity. THE OS does not inspect the application's undo history or claim what operation was reversed. At this boundary `CTRL_Y` and `CTRL_S` were still blocked; boundary 44 later adds them through the registry-driven engine.
43. **Registry-driven Keyboard Engine v1** — foreground Ctrl+letter shortcut policy is centralized in one immutable `WindowShortcutSpec` registry. Labels, user-facing preview warnings, local `ActionRisk`, catalog enum/description, clipboard/content-effect evidence, and Windows virtual-key transport mapping are derived from that registry instead of repeated per-shortcut branches. The legacy `window_shortcuts` module remains as a compatibility facade. Existing CTRL+A/C/X/V/Z behavior is unchanged; adding another supported Ctrl+letter shortcut now requires a registry entry rather than coordinated edits across action, catalog, adapter, and policy tests.
44. **Registry-driven shortcut batch 1** — the Keyboard Engine v1 adds `CTRL_F` (find), `CTRL_S` (save), and `CTRL_Y` (redo) through registry entries rather than new transport branches. `CTRL_F` is `CONFIRM`; `CTRL_S` and `CTRL_Y` are `DESTRUCTIVE` because they may persist or reapply content changes. All three inherit the existing exact PID/title/target-token guard, fixed four-event Ctrl+letter transport, foreground verification, no clipboard API reads, and no semantic application-content verification. `Alt+F4` and arbitrary unregistered combinations remain blocked.
45. **Registry-driven single-key policy** — the Keyboard Engine now centralizes `press_key` policy in an immutable `WindowKeySpec` registry. Allowed keys, local risk, preview text, and ToolCatalog schema/description are derived from that registry, while the Windows adapter keeps the virtual-key mapping as a separate transport concern. Existing ENTER/ESCAPE/TAB/navigation/editing behavior is unchanged, and generic tests require transport coverage for every registered key.

46. **Registry-driven Ctrl navigation chord batch** — the Keyboard Engine extends `press_shortcut` with `CTRL_LEFT`, `CTRL_RIGHT`, `CTRL_UP`, `CTRL_DOWN`, `CTRL_HOME`, and `CTRL_END` as one coherent navigation batch. All six remain `CONFIRM`, use the same exact PID/title/target-token guard and the same fixed four-event Ctrl shortcut transport, and do not introduce a new `press_shortcut` execution branch. The registry now permits a shortcut primary key to be either an A-Z letter or a key already registered by the single-key engine; the Windows adapter resolves those registered special keys through its existing virtual-key transport map. Semantic cursor/document position is not inspected or claimed.

47. **Registry-driven Mouse Engine v1 center click** — THE OS introduces `click_window` for one exact visible target guarded by PID, bounded title, and opaque target token. Mouse button policy is centralized in an immutable `MouseButtonSpec` registry with `LEFT`, `RIGHT`, and `MIDDLE`, all `CONFIRM`. This first boundary deliberately fixes the position to the geometric center of the exact window: the Windows adapter re-resolves and foregrounds the approved target, obtains its rectangle locally, moves the cursor to the center, verifies that cursor position, sends exactly one button-down/up pair, and verifies foreground continuity. Arbitrary coordinates, double-click, drag, wheel, screenshots, control inspection, and semantic effect claims remain blocked.

48. **Bounded Mouse Engine v1 center wheel scroll** — THE OS adds `scroll_window` for `UP` and `DOWN` as registry-driven `CONFIRM` operations against the same exact PID/title/opaque-token window identity. Each execution reactivates and verifies the approved target, computes and verifies the geometric center cursor position, then submits exactly one `MOUSEEVENTF_WHEEL` event with a fixed local magnitude of one Windows wheel delta (`120` or `-120`). Arbitrary scroll amount, horizontal wheel, arbitrary coordinates, drag, double-click, screenshots, control inspection, and semantic scroll-result claims remain blocked.

49. **Registered internal client-area click anchors** — THE OS adds `click_window_anchor` without changing the already-closed `click_window` center transport. The new tool accepts one exact PID/title/opaque-token target, a registered mouse button, and one of four immutable internal client-area anchors: `UPPER_LEFT`, `UPPER_RIGHT`, `LOWER_LEFT`, or `LOWER_RIGHT`. Those points are fixed at 25%/75% of client width and height, so no arbitrary x/y or edge/title-bar coordinate enters the schema. The Windows adapter revalidates and foregrounds the exact target, reads only client geometry, converts the client origin to screen coordinates locally, verifies the cursor at the derived anchor, sends exactly one button-down/up pair, and verifies foreground continuity. Existing center click and center wheel methods remain unchanged; screenshots, control inspection, drag, double-click, arbitrary coordinates, and semantic effect claims remain blocked.

50. **Bounded center double-click gesture** — THE OS adds `double_click_window` as a separate `CONFIRM` action without changing the existing single-click, anchor-click, or wheel transports. This boundary registers only `DOUBLE_LEFT`, fixes the target position to the geometric center of the exact PID/title/opaque-token window, and emits exactly four SendInput events in the sequence LEFT down/up/down/up. The schema exposes no arbitrary button, click count, timing interval, x/y, anchor, drag, or wheel parameter. Success verifies cursor position, four-event submission, and exact foreground continuity only; THE OS explicitly does not claim that the application recognized a semantic double-click or what effect it caused.

51. **Registered anchor double-click composition** — THE OS adds `double_click_window_anchor` by composing two already-closed mechanisms without altering either one: the `DOUBLE_LEFT` four-event gesture and the four internal client-area anchors at fixed 25%/75% fractions. The tool accepts only exact PID/title/opaque-token identity, `DOUBLE_LEFT`, and one registered anchor. The Windows adapter revalidates and foregrounds the target, obtains client geometry, converts its origin to screen coordinates locally, derives the registered anchor, verifies the cursor, submits exactly LEFT down/up/down/up, and verifies foreground continuity. Arbitrary coordinates, click counts, timing intervals, buttons, drag, screenshots, control inspection, and semantic double-click claims remain blocked. Existing center click, anchor click, center wheel, and center double-click methods remain unchanged.

52. **Destructive registered anchor-to-anchor drag** — THE OS adds `drag_window_anchor` as the first bounded drag mechanism and classifies its sole registered gesture, `LEFT_DRAG`, as `DESTRUCTIVE` because dragging may select, move, reorder, or otherwise alter application content. Both source and target must be different registered client-area anchors at fixed 25%/75% fractions. Execution revalidates and foregrounds the exact PID/title/opaque-token window, derives and verifies the source, submits exactly one LEFTDOWN, derives and verifies the destination while the button is held, then submits exactly one LEFTUP and verifies foreground continuity. Arbitrary coordinates, paths, duration, buttons, event counts, screenshots, control inspection, and semantic drag claims remain blocked; all previously closed mouse transport methods remain unchanged.

53. **Registered internal anchor wheel composition** — THE OS adds `scroll_window_anchor` by composing the already-closed one-unit `UP`/`DOWN` wheel policy with the four registered internal client-area anchors at fixed 25%/75% fractions. The new action remains `CONFIRM`, accepts only exact PID/title/opaque-token identity, one registered direction, and one registered anchor, then revalidates and foregrounds the target, derives and verifies the client-area anchor, submits exactly one fixed-magnitude `MOUSEEVENTF_WHEEL` event, and verifies foreground continuity. 54. **Registered internal anchor cursor movement** — THE OS adds `move_cursor_window_anchor` as a confirmation-gated pointer-only operation. It accepts only exact PID/title/opaque-token identity and one of the four registered client-area anchors at fixed 25%/75% fractions. Execution revalidates and foregrounds the target, derives the anchor from local client geometry, calls `SetCursorPos`, verifies the exact final position with `GetCursorPos`, and verifies foreground continuity. It emits zero `SendInput` events and no button, wheel, key, duration, path, or arbitrary x/y enters the schema. Applications may react to hover, but THE OS does not inspect or claim any hover or content effect; all previously closed mouse transport methods remain unchanged.

55. **Eight-point registered internal anchor grid** — THE OS expands the shared client-area anchor registry from the original four quadrant points to an eight-point 3×3 interior grid with the exact client center deliberately omitted. The registered positions are `UPPER_LEFT` (25%/25%), `TOP_CENTER` (50%/25%), `UPPER_RIGHT` (75%/25%), `CENTER_LEFT` (25%/50%), `CENTER_RIGHT` (75%/50%), `LOWER_LEFT` (25%/75%), `BOTTOM_CENTER` (50%/75%), and `LOWER_RIGHT` (75%/75%). Because click, double-click, wheel, pointer movement, and drag already consume the registry, all five anchor-based mechanisms inherit the expanded geometry without changing their Windows transport methods. The exact `(50%, 50%)` client center remains reserved rather than becoming an anchor, arbitrary x/y remains blocked, and one pointer-only `TOP_CENTER` live test represents the same registry extension across the batch.

56. **Registered Window Layout Engine v1** — THE OS adds `place_window` for deterministic normal-risk window geometry on the target's current monitor. The local immutable registry exposes only `LEFT_HALF`, `RIGHT_HALF`, `UPPER_LEFT_QUADRANT`, `UPPER_RIGHT_QUADRANT`, `LOWER_LEFT_QUADRANT`, and `LOWER_RIGHT_QUADRANT`. Execution re-resolves the exact PID/title/opaque-token target, restores it from minimized or maximized state when necessary, obtains only the current monitor's usable `rcWork`, derives the requested half or quadrant locally, applies it with `MoveWindow`, and requires `GetWindowRect` to match the calculated rectangle exactly. The model cannot supply x/y, width/height, pixels, monitor IDs, or arbitrary percentages. Existing minimize, maximize, restore, keyboard, and mouse transports remain unchanged, and THE OS does not claim Windows native Snap semantics beyond the verified geometry. During window-oriented requests, the tool loop also withholds `open_application` unless the original user turn contains explicit launch intent; a second local guard blocks a provider that proposes launching an application despite that tool not being advertised, preventing accidental duplicate application instances while operating on an existing window.

57. **Window Layout Engine v2 spatial batch** — the shared immutable placement registry expands from six to eleven monitor-work-area layouts without changing the Windows transport. `TOP_HALF` and `BOTTOM_HALF` add horizontal halves, while `LEFT_THIRD`, `CENTER_THIRD`, and `RIGHT_THIRD` partition the full work-area width into registered 0%→33%, 33%→67%, and 67%→100% bands; the center band is 34% so the three registered intervals close exactly at 100%. The original left/right halves and four quadrants remain unchanged. `place_window` continues to accept only a placement name plus exact PID/title/opaque-token identity; x/y, width/height, percentages, pixels, and monitor selection remain absent from the schema. The existing `MonitorFromWindow` → `GetMonitorInfoW(rcWork)` → `MoveWindow` → exact `GetWindowRect` verification path is unchanged byte-for-byte.

58. **Multi-target filtered visible-window discovery** — THE OS adds `window_snapshot_many` as a separate confirmation-gated discovery tool for tasks that name several existing windows. It accepts exactly 2–4 distinct bounded literal filters, enumerates visible titled top-level windows once, and locally keeps only windows whose bounded title or process name contains at least one requested filter using deterministic case-insensitive substring matching. The union is capped globally at 12 results and preserves Windows z-order. Evidence includes only title, process name, PID, opaque target token, filter metadata, and per-query match counts; hidden-window titles, screenshots, content, keystrokes, executable paths, and raw HWND values remain excluded. The original single-filter/unfiltered `window_snapshot` transport remains unchanged, so multi-window workflows can discover several exact targets under one privacy confirmation without broadening to an unfiltered desktop snapshot.

59. **Transactional two-window layout engine v1** — THE OS adds `place_window_pair` for organizing two already-discovered exact windows on the same monitor under one normal-risk action. The immutable pair-layout registry exposes `SIDE_BY_SIDE` (first `LEFT_HALF`, second `RIGHT_HALF`) and `STACKED` (first `TOP_HALF`, second `BOTTOM_HALF`). Follow-up identity is token-only: the model supplies exactly two distinct opaque `target_token` values plus the registered arrangement, and the adapter locally re-enumerates visible windows and recovers each PID/title from the exact HMAC token instead of accepting independently supplied PID/title fields that could be mixed between duplicate-titled candidates. For hosted Windows apps, a selected `Windows.UI.Core.CoreWindow` or stale `ApplicationFrameWindow` is normalized locally to exactly one same-title `ApplicationFrameWindow` that is non-minimized, non-maximized, and has a positive client area; zero or multiple eligible visual frames block the action. Both resolved targets must be distinct, visible, on the same monitor, and already in normal state; minimized or maximized targets are blocked before any movement so rollback remains exact. The adapter resolves both tokens in one local `EnumWindows` pass, records both original rectangles, derives both registered rectangles from the shared monitor `rcWork`, applies them with `MoveWindow`, and requires exact `GetWindowRect` verification for each. If a failure occurs after mutation begins, it attempts to restore both original rectangles and verifies that rollback before returning the original failure; an unverifiable rollback is surfaced separately. Arbitrary coordinates, size, percentages, monitor selection, screenshots, input injection, and native Snap-semantic claims remain excluded, while the existing single-window `place_window` and multi-target discovery transports remain unchanged.
60. **Transactional multi-window layout engine v1** — THE OS adds `place_window_set` for atomic registered arrangements of three or four already-discovered exact windows, completing the 2–4-target discovery/composition path without changing the closed two-window engine. The registry exposes `THREE_COLUMNS`, `LEFT_MAIN_RIGHT_STACK`, `RIGHT_MAIN_LEFT_STACK`, and `FOUR_QUADRANTS`, all derived only from the existing eleven registered placement rectangles. The schema accepts only an ordered array of 3–4 distinct opaque `target_token` values plus the registered arrangement. Execution resolves every token in one local `EnumWindows` pass, applies the existing hosted-window `CoreWindow` → unique operable `ApplicationFrameWindow` normalization, blocks duplicate resolved frames, LYRA itself, minimized/maximized targets, mixed monitors, invalid work areas, and count/layout mismatches before mutation. All original rectangles are captured first; every `MoveWindow` result is verified by exact `GetWindowRect`, and any partial failure triggers verified rollback of the entire set. Arbitrary coordinates, sizes, pixels, percentages, monitor selection, screenshots, input injection, and native Snap-semantic claims remain excluded; `place_window`, `place_window_pair`, and `window_snapshot_many` remain unchanged.
61. **Shared hosted-window resolution v2** — the two-window and multi-window transactional layout engines now share one conservative hosted-app visual-frame resolver. The pre-existing same-title `CoreWindow`/`ApplicationFrameWindow` normalization remains primary; only when that resolver would otherwise block because multiple operable same-title frames exist does the shared v2 policy consult local DWM cloaking metadata. Exactly one `DWM_CLOAKED=0` candidate resolves the ambiguity, while zero or multiple uncloaked candidates remain blocked. A single otherwise-eligible frame is never rejected merely because its DWM cloaking value is nonzero or unavailable. `place_window_pair` now records whether the DWM tie-break was used and the resolved cloaking values, and its provider guidance distinguishes hosted aliases from genuinely distinct windows just like `place_window_set`. The single-window `place_window`, window discovery, keyboard, and mouse transports remain unchanged.
62. **Single-window hosted placement parity** — `place_window` now resolves an exact application-specific `Windows.UI.Core.CoreWindow` token to the same-title visual `ApplicationFrameWindow` before applying registered geometry, closing the hosted-app gap left intentionally by M61. Unlike the transactional pair/set engines, the single-window action preserves its existing ability to restore minimized or maximized targets: a directly selected `ApplicationFrameWindow` remains the exact target even when not normal, while a selected CoreWindow may resolve to a same-title positive-client-area frame regardless of minimized/maximized state and then use the existing restore path before `MoveWindow`. Multiple candidate frames use the same conservative local DWM principle: exactly one `DWM_CLOAKED=0` frame resolves ambiguity; zero or multiple uncloaked frames block. The tool takes no model arguments and is pinned to the M91-authorized HTTPS repository, source `refs/heads/main`, and destination `refs/remotes/origin/main`. Preview is local-only: it revalidates M91, rejects shallow repositories and local transport/fetch overrides, and binds local HEAD, the complete local-ref digest, working-tree/index status digest, current tracking-ref state, and concrete `git.exe` identity. After confirmation, execution obtains the remote SHA via M92, performs a fixed object-only fetch with no tags, submodules, FETCH_HEAD write, commit-graph write, or auto-maintenance, and requires that no ref, working-tree, or index state changed during that fetch. It then re-reads M92; only if the remote SHA stayed stable may the tool atomically set the one authorized remote-tracking ref. Existing tracking state may move only fast-forward. System/global Git config, inherited proxy/Git environment knobs, credential helpers, and askpass are denied for the fetch transport. Success proves HEAD/branch, index, working tree, and every other ref stayed unchanged. No pull or push authority is introduced.

The model never receives arbitrary shell execution. Tool calls are proposals only. The local `ToolCatalog` is an allowlist and `ActionRegistry` remains the execution authority.

Risk classification is also local authority. Launching shells or administrative system tools through `open_application` is classified as `CONFIRM`, while ordinary applications such as Notepad and Calculator remain `NORMAL`. Application-name normalization is deterministic and shared by resolution and risk classification: repeated whitespace is collapsed and at most one leading Portuguese article (`a`, `o`, `um`, `uma`) is removed before alias lookup or risk evaluation. This does not perform fuzzy matching or infer an application when only an article such as `um` is supplied. Calculator is a specific registry alias: the local launch target remains `calc.exe`, while verification accepts the launcher plus the bounded known runtime process names `CalculatorApp.exe` and `Calculator.exe`. For `open_path`, executable, script, shortcut, installer, and similar suffixes are also classified as `CONFIRM`.

Filesystem search is intentionally bounded: name search starts only from the root explicitly supplied to the tool, is depth-limited, and caps the number of matches. `inspect_path` returns metadata and a bounded directory listing.

Literal content search is separately privacy-gated. `search_text` requires an explicit root plus one single-line literal query and confirmation before any file content is touched. It scans only within fixed depth/file/byte/result ceilings, does not follow symlinks or junctions, skips known credential/key paths, ignores binary/unsupported text, and returns only bounded line snippets marked as untrusted data. If any ceiling, access error, sensitive-path/link exclusion, or per-file prefix limit prevents exhaustive traversal, the result is explicitly marked partial.

`read_text_file` is deliberately not automatic even though it is read-only at the filesystem level. File contents are returned to the configured AI provider as tool data, so every read requires local confirmation before the file is touched. Known credential/key paths such as `.env`, private-key names, `.pem`, `.key`, `.p12`, and `.pfx` are classified as `PRIVILEGED`. The tool reads at most 16 KiB, rejects binary-looking data, and marks returned content as untrusted data so text inside a file is not authority to execute more actions.

`read_text_lines` uses the same privacy gate for targeted context. It accepts only a path, a 1-based start line, and a maximum of 40 lines; it scans no more than 256 KiB to reach that range and returns no more than 16 KiB. When a requested line is beyond the scan ceiling, THE OS reports an indeterminate bounded-scan failure rather than misreporting the line as absent. Returned numbered lines remain untrusted data and grant no follow-up authority.

`check_python_syntax` is a separate confirmation-gated verification primitive for `.py` and `.pyw` files up to 256 KiB. It reads the source locally only after approval, honors Python's source-encoding detection rules, and compiles without executing or importing the file. No source line is returned even on failure; only bounded structural diagnostics such as line/offset and the compiler message are exposed, and those diagnostics remain untrusted data. The verifier writes no bytecode or `__pycache__`.

`check_python_static` is the next verification layer but does not inherit general subprocess authority. It invokes only the Ruff executable colocated with the active venv Python, passes a fixed isolated/no-cache/no-fix argv for py314 and E4/E7/E9/F, accepts only one bounded Python file path, and uses no shell. The target is hashed before and after the process; a changed target invalidates the result. Provider-visible output is capped to 20 structural diagnostics and omits source lines, raw verifier streams, and fix edit contents.

`check_python_static_many` reuses that same verifier for one explicit 2–8-file batch. It does not accept a directory or project root: every path is individually supplied and preflighted, with a 256 KiB per-file ceiling and 1 MiB total ceiling. One Ruff process receives only the fixed M72 flags plus those absolute approved paths. All targets are hash-guarded before/after, and provider-visible diagnostics are capped globally at 40 and mapped only to the approved file set.

`run_python_unit_test_file` crosses a different authority boundary and is therefore always `PRIVILEGED`: pytest executes the selected test module and whatever Python it imports with the current user's permissions. THE OS does not claim a sandbox. The local preview hashes the exact explicit `tests/unit/test_*.py` target and approval carries that path/SHA guard into execution. The runner uses only the venv-adjacent `pytest.exe` with fixed no-shell, no-plugin-autoload, no-conftest, no-cacheprovider arguments and one exact file path. Raw pytest streams are discarded; only bounded JUnit counts return to the provider.

Pytest failure evidence is separately bounded. THE OS may expose at most three untrusted JUnit diagnostics from the already-authorized run, each limited to outcome kind, bounded testcase/class names, and the bounded `message` attribute. The XML body of failure/error elements is never returned, so pytest traceback text, source context, captured streams, and locals remain outside provider-visible evidence. This changes observation only; it does not widen what pytest may execute.

The pytest approval also carries a bounded project-Python state digest. THE OS hashes only `.py` files under the fixed `src/theos` and `tests/unit` roots, subject to a 256-file, 256-KiB-per-file, 4-MiB-total ceiling, and returns no per-file manifest entries or source text. The same manifest must match immediately before execution and after pytest completes. A change blocks startup or invalidates the result respectively. This guard covers the project's primary Python code/test roots but is not presented as a full dependency closure or side-effect sandbox.

Controlled pytest invocation also ignores ambient pytest option sources. THE OS supplies its own minimal temporary config with `-c`, pins `--rootdir` to the checkout, clears inherited `PYTEST_*` variables, re-enables only plugin-autoload disabling, and passes `--disable-plugin-autoload` explicitly. This prevents project pytest config, `PYTEST_ADDOPTS`, and `PYTEST_PLUGINS` from silently widening collection or startup plugins for the controlled run. It does not make Python imports hermetic and does not change the privileged/no-sandbox classification.

The child Python environment is also narrowed without pretending to be hermetic. All inherited `PYTHON*` variables are removed, then only `PYTHONDONTWRITEBYTECODE=1`, `PYTHONNOUSERSITE=1`, and `PYTHONSAFEPATH=1` are supplied. This removes inherited `PYTHONPATH`/`PYTHONHOME` and other interpreter knobs, disables the user site, and asks Python not to prepend potentially unsafe script/current-directory paths. The venv's own site-packages and startup behavior are still part of the privileged runtime and are not treated as a sandbox or complete dependency closure.

The fixed pytest launcher is also approval-bound by identity. THE OS hashes the non-link venv-sibling `pytest.exe` during preview, requires the approved path/SHA immediately before process creation, and rechecks the launcher after the run. Verifier bytes are never provider-visible. This protects the verifier executable from replacement across the approval/run window but does not attest the rest of the venv or operating-system loader chain.

The core pytest package code is separately approval-bound with a bounded manifest over only the fixed `pytest` and `_pytest` roots in the active venv site-packages. That digest is checked before and after the privileged run, while file contents and per-file entries remain local. This narrows package-code replacement across the approval/run window, but it is intentionally not a full dependency closure: other installed packages, interpreter/loader components, and startup hooks outside those roots remain privileged external state.

The venv bootstrap itself is also approval-bound at the two fixed files that select and redirect the Python runtime: `Scripts/python.exe` and the venv-root `pyvenv.cfg`. Their local hashes are combined into a guarded state digest and rechecked before and after pytest. This does not attest the base Python installation, DLLs, operating-system loader, or the rest of the venv, so THE OS still does not claim runtime dependency closure or sandboxing.

For cohesive verification of a small change, `run_python_unit_test_files` may compose that same hardened single-file runner over 2–4 explicit tests under one privileged approval. The batch is locally distinct after path resolution, capped at 768 KiB selected bytes, and never turns into a directory or project selector. Each approved file receives its own pytest subprocess and the full existing state guards; the batch therefore widens only how many explicit test files one confirmation may authorize, not executable choice, flags, shell authority, or collection scope.

Git capability begins read-only. `git_status_snapshot` is pinned to the current THE OS checkout and exposes only a bounded structural working-tree snapshot after confirmation. The executable path/SHA is locally approval-bound, inherited Git redirection variables are removed, optional locking is disabled, and fixed argv is used without a shell. This boundary intentionally provides no diff content and no Git mutation authority; it establishes repository identity and status evidence before later local staging/commit capabilities are considered.

`git_diff_file` adds the next read-only review layer for one already-tracked changed file. Its confirmation preview shows only path/hash/HEAD/executable metadata; actual diff content is collected only after approval, bounded to 32 KiB/400 lines, and treated as untrusted data. The request cannot carry a revision, ref, command, option, repository, or executable, and post-read revalidation discards a diff if the file, HEAD, or Git executable changed during collection. Untracked/deleted/binary targets deliberately remain outside this first diff boundary.

`git_stage_file` is the first mutable Git-local boundary and deliberately stops at the index. It can stage only one already-tracked unstaged modification while the entire index is empty; it cannot add a new file or compose a batch. Approval is bound to the exact file bytes, HEAD, and `git.exe` identity, and the fixed mutation is post-verified as exactly one staged path with unchanged working-tree bytes. Its only compensating mutation is a same-path reset after a failed postcondition; no commit or remote operation is reachable from this tool.

`git_unstage_file` provides the matching bounded recovery direction for the first staging boundary. It accepts only the sole staged tracked modification, binds file bytes/HEAD/`git.exe` at approval, and executes only a fixed same-path reset to HEAD. The successful postcondition is an empty index plus the same working-tree bytes now represented as an unstaged modification. If that exact state cannot be verified, the only compensation is re-staging the same approved path; commit and remote authority remain unreachable.

`git_stage_new_file` adds only the missing single-file creation edge to the bounded index model. It cannot modify file contents or choose a repository, ref, revision, command, flag, executable, or remote; it may only convert one approved `??` path into the sole `A ` entry in the index. Approval binds file bytes, HEAD, and `git.exe`, and failed post-validation can only reset that same path back to untracked. Commit and remote authority remain unreachable.

`git_unstage_new_file` completes the reversible single-new-file index edge introduced by M87. It may only turn the sole approved staged addition back into the same untracked file, without changing its bytes. Approval remains bound to file content, HEAD, and `git.exe`; failure compensation can only re-stage that same path. No commit or remote authority is introduced.

`git_commit_staged_file` crosses from reversible index mutation into local history, so its authority is deliberately narrower than a general `git commit`. The model cannot provide a path, message, option, ref, repository, executable, or remote; exactly one previously staged tracked modification defines the entire commit payload. Hooks are redirected to a temporary empty directory and signing is disabled so commit-time extension points do not silently add execution authority. Once HEAD advances, the action never attempts an automatic reset or amend as compensation; ambiguous or failed post-validation becomes a stop condition for explicit recovery.

`git_commit_staged_new_file` completes the first bounded local-history pair by allowing the already-bounded `A ` state from M87 to become one local commit. Like the tracked-file commit boundary, it takes no model arguments, uses a fixed local subject, disables hooks and signing, and never grants remote authority. Its extra postcondition explicitly proves that the previously new path became tracked and clean while retaining the exact approved bytes. Any ambiguous state after HEAD advances is preserved for explicit reconciliation rather than automatically reset.

`git_remote_identity_snapshot` separates remote identity from remote contact. Before THE OS is allowed to ask GitHub what `main` currently points to, it can prove locally that its own checkout names exactly the one authorized HTTPS origin and tracking ref, with no local push redirection or URL rewrite knobs that would silently change the destination. The tool intentionally returns no arbitrary mismatching config values and performs no network I/O; later remote-read and remote-write milestones must revalidate this identity rather than treating M91 as durable authorization.

`git_remote_head_snapshot` is deliberately narrower than `git fetch`. It observes one public remote ref without importing objects or moving any local ref. The network subprocess is launched outside the repository so local Git config cannot influence transport behavior, while system/global config and interactive credential paths are disabled as well. This gives later delivery logic a bounded freshness fact — the current remote `main` SHA — without yet granting synchronization or write authority.

`git_fetch_remote_main` separates object import from ref mutation so the network subprocess itself is not allowed to move any local ref. The remote SHA is observed before and after object transfer; `refs/remotes/origin/main` is then advanced with an atomic expected-old-value guard and only when that move is fast-forward (or the ref was absent). The first live proof may deliberately start with that single remote-tracking ref absent so restoration by the product demonstrates the bounded mutation without touching `main`, HEAD, the index, or working-tree bytes.

`write_text_file` accepts only a complete replacement body of at most 16 KiB. Before approval, THE OS resolves the target locally, verifies that its parent exists, rejects directories, binary-looking existing files, and existing files larger than the bounded limit, then produces a unified diff for ordinary files. Sensitive paths use a redacted local preview so secrets are not printed into the LYRA chat. New ordinary files are `CONFIRM`, existing ordinary files are `DESTRUCTIVE`, and sensitive or executable/script-like paths are `PRIVILEGED`.

`replace_text_literal` is the surgical counterpart for existing files up to 256 KiB. It can replace or remove only one unique nonblank single-line literal at a time, with both proposal strings bounded to 1024 characters. Zero or multiple matches are blocked before confirmation. Ordinary previews use a bounded unified diff, with a focused old/new literal fallback when oversized context would otherwise hide the exact change. The approved mutation is bound to original/result SHA-256 values and the proposal hashes, then published atomically and verified. The adapter preserves the detected source encoding and does not normalize untouched line endings. Script/code targets remain `PRIVILEGED` but may show the local diff; credential/key paths keep their textual preview redacted.

`replace_text_block` extends that guarded model only to bounded multiline blocks. Matching canonicalizes newline spellings for comparison, then maps the one unique canonical match back to the original source span; bytes/text outside that decoded span are not reconstructed from normalized content. The replacement block adopts the matched/file newline convention, while the rest of the file retains its original newline sequences. Both blocks are limited to 1024 characters and 40 lines, and the same 256 KiB file ceiling, preview/guard model, atomic publication, verification, risk escalation, and credential redaction apply.

Approval carries a local execution guard containing the resolved path and hashes from the preview. If the target or proposed content changes between preview and execution, the write is blocked. Successful writes use a same-directory temporary file plus `os.replace`, then verify the resulting SHA-256. The tool never creates missing parent directories.

Copy is also bounded and verified. `copy_path` supports ordinary files and recursive directory trees up to 256 entries and 64 MiB total. Symbolic links and Windows junctions are rejected, existing destinations are never overwritten, and a content manifest is recalculated before and after the copy. The copied result is built at a temporary sibling path and published to the requested destination only after verification. Ordinary copies are `CONFIRM`; sensitive/executable or protected-system locations are `PRIVILEGED`.

System status is deliberately narrow. `system_status` reports a single read-only resource snapshot: CPU utilization, logical/physical CPU counts, memory usage, the Windows system-drive usage, and battery percentage/power state when the hardware exposes it. It does not list processes, inspect windows, read arbitrary environment variables, change power settings, or perform any other system mutation.

Process inspection is privacy-gated. `process_snapshot` does not enumerate anything during the preview; after explicit confirmation it collects only process name, PID, and resident memory (RSS), sorts locally by RSS, and returns at most 12 entries to the AI provider. Executable paths, command lines, usernames, environment data, network connections, and open-file lists are intentionally excluded.

Process termination is intentionally narrow and destructive. `terminate_process` requires an exact PID, prepares a local preview containing the process name and PID, warns that unsaved work may be lost, and carries a PID/name/creation-time guard into execution. LYRA blocks its own process plus a conservative set of protected Windows processes, revalidates identity immediately before termination, waits up to three seconds for exit, and does not escalate to a separate kill fallback.

Visible-window inspection is privacy-gated. `window_snapshot_many` provides a separate 2–4-filter path for several named windows under one confirmation and one local enumeration, while `window_snapshot` preserves its existing unfiltered/single-filter behavior. `window_snapshot` performs no desktop enumeration during its confirmation preview. After approval, it inspects only visible top-level windows that have non-empty titles, preserves Windows z-order, truncates each title to 160 characters, and returns at most 12 entries containing title, process name, PID, and a process-local opaque HMAC target token. When the user is looking for a specific window, the tool may carry an optional literal query of at most 80 characters; THE OS applies a case-insensitive substring match locally against only the bounded title and process name before the 12-result cap. This avoids losing a requested window merely because it sits below the first 12 entries in z-order without increasing provider-visible window metadata. The filter is not regex or fuzzy matching and does not remove the confirmation gate. The token lets later gated actions distinguish windows that share the same PID and bounded title without returning the raw Windows handle. The snapshot does not capture pixels, window contents, keyboard input, hidden-window titles, executable paths, command lines, usernames, environment data, or raw window handles.

Visible-window activation is intentionally narrow. `activate_window` accepts only the exact PID, bounded title, and opaque `target_token` produced by `window_snapshot`. THE OS revalidates exactly one requested identity locally; for a hosted CoreWindow alias only, it may then normalize to the visual ApplicationFrameWindow before restoring a minimized frame, requesting foreground activation, and verifying that resolved visual target as the Windows foreground window. Raw window handles remain local. This action is `NORMAL`: it changes focus but does not modify files, terminate processes, type input, or interact with controls inside the window.

Foreground key input is deliberately risk-gated and allowlisted. `press_key` accepts the exact PID, bounded title, and opaque `target_token` from `window_snapshot`, and accepts only `ENTER`, `ESCAPE`, `TAB`, `UP`, `DOWN`, `LEFT`, `RIGHT`, `HOME`, `END`, `PAGE_UP`, `PAGE_DOWN`, `BACKSPACE`, or `DELETE`. Navigation/control keys remain `CONFIRM`; `BACKSPACE` and `DELETE` are locally classified `DESTRUCTIVE` because the focused control may lose content. The preview names the exact key and target and carries a PID/title/token/key execution guard. After approval, execution revalidates that exact requested identity, normalizes a hosted CoreWindow to its visual frame only when needed, restores and foregrounds the resolved frame, and verifies foreground before sending one virtual-key down/up pair with `SendInput`. Success means Windows accepted both events and the resolved visual target remained foreground. THE OS does not expose raw window handles, send modifiers or shortcuts, or read application contents to claim what the key caused inside the target.

Single-key policy is registry-driven. `WindowKeySpec` is the single policy source for each supported key's intent, local `ActionRisk`, and user-facing preview warning. `PressKeyAction` and `ToolCatalog` consume registry-derived policy, while the Windows adapter retains only the explicit virtual-key transport mapping. Generic tests require the transport map to cover every registered key, preserving the separation between policy and Windows mechanism.

Foreground shortcut input is separate from `press_key` and deliberately narrow. `press_shortcut` accepts the registered Ctrl shortcuts for select/copy/cut/paste/undo/find/save/redo plus the navigation chord batch `CTRL_LEFT`, `CTRL_RIGHT`, `CTRL_UP`, `CTRL_DOWN`, `CTRL_HOME`, and `CTRL_END`; every request still requires the exact PID, bounded title, and opaque `target_token` from `window_snapshot`. The navigation chords are `CONFIRM`; existing destructive and privileged classifications remain unchanged. The local preview and execution guard bind PID/title/token/shortcut. After approval THE OS revalidates the exact requested identity, applies hosted visual-frame normalization only when needed, restores and foregrounds that resolved frame, and sends exactly one fixed four-event Ctrl shortcut sequence through `SendInput`. Partial submission triggers a best-effort release of the primary key and Ctrl before failure is reported. THE OS does not call clipboard APIs or expose clipboard contents to the AI provider and does not verify semantic application effects. Unlisted shortcuts remain blocked.

Keyboard shortcut policy is registry-driven. `WindowShortcutSpec` is the single source for each supported Ctrl shortcut's label, primary key, local risk, intent, preview warning, and effect metadata. A primary key may be an A-Z letter or a key already registered by the single-key engine; Windows virtual-key resolution remains a separate adapter transport concern. `PressShortcutAction`, `ToolCatalog`, and the Windows adapter consume derived registry data, while `window_shortcuts` remains only a compatibility facade. Existing transport invariants remain fixed: exact opaque target, four SendInput events, foreground verification, no arbitrary modifier sequence, no clipboard API reads, and no semantic application-content inspection.

Mouse input is separately confirmation-gated and registry-driven. `click_window` accepts only an exact PID/title/target-token target and a registered button (`LEFT`, `RIGHT`, or `MIDDLE`) at the geometric center of the full window. `click_window_anchor` is separate and uses the shared eight-point registered interior client-area grid at fixed 25%/50%/75% fractions with the exact client center omitted; it never accepts x/y or pixels. `scroll_window` accepts the same exact target plus registered `UP` or `DOWN` wheel direction at the geometric center. `double_click_window` is a separate registered gesture tool that currently permits only `DOUBLE_LEFT` at the geometric center and always sends the fixed four-event LEFT down/up/down/up sequence. `double_click_window_anchor` composes that same fixed gesture with the shared eight-point registered client-area grid, without exposing coordinates or timing. `drag_window_anchor` adds one destructive `LEFT_DRAG` operation from one registered client anchor to a different registered client anchor using exactly one LEFTDOWN and one LEFTUP around the verified cursor move. `scroll_window_anchor` composes the existing one-unit UP/DOWN wheel transport with one registered point from the shared eight-point client-area grid while leaving center scroll unchanged. `move_cursor_window_anchor` adds a pointer-only move to one registered point from the shared eight-point client-area grid with zero SendInput events and no semantic hover claim. Before geometry or input, every mouse action revalidates the exact requested identity and, only for a hosted CoreWindow alias, normalizes to the visual frame that is then restored/foregrounded. Center click and anchor click still send exactly two button events; center or anchor scroll still sends exactly one fixed-magnitude wheel event; double-click still sends exactly four button events; drag still sends exactly two button events separated by one bounded anchor-to-anchor cursor move; pointer-only movement still sends no input event. Success verifies geometry, transport, and focus only; THE OS does not read controls or claim semantic application effects.

Foreground text input is deliberately confirmation-gated. `type_text` accepts the exact PID, bounded title, and opaque `target_token` from `window_snapshot`, plus a literal body of at most 512 Unicode characters. Its static local preview shows the target and text and carries a PID/title/token/content-hash execution guard. After approval, execution revalidates that exact requested identity, normalizes a hosted CoreWindow alias to the visual frame only when needed, restores and foregrounds the resolved frame, and verifies it before input. THE OS emits only `SendInput` Unicode key events and rejects Enter, Tab, other control characters, shortcuts, and special keys; it does not use the clipboard and blocks LYRA's own requested process window. Success means Windows accepted the complete input event sequence and the resolved visual target remained foreground. Raw window handles stay local, and THE OS intentionally does not read window/control contents or claim where the characters appeared.

Registered window placement is also intentionally bounded. `place_window` accepts one of eleven registry-defined monitor-work-area layouts (left/right/top/bottom half, left/center/right third, or one of four quadrants), derives geometry locally, and verifies the final window rectangle exactly; arbitrary coordinates, size, percentages, monitor selection, and native Snap-semantic claims are excluded. For a hosted app, single-window placement keeps its exact PID/title/token guard but may resolve an application-specific CoreWindow alias to the same-title visual ApplicationFrameWindow before restoring state and moving it; directly selected frames retain the existing restore semantics. `place_window_pair` separately composes two exact normal-state windows on the same monitor into a registered `SIDE_BY_SIDE` or `STACKED` arrangement; its schema accepts only two opaque target tokens plus the arrangement, re-resolves PID/title locally from those tokens, records both original rectangles before mutation, and uses verified local rollback if a partial pair move fails. `place_window_set` extends the same bounded composition model to registered 3–4-window arrangements using only an ordered token array plus the arrangement; it resolves all targets in one local enumeration, requires one shared monitor and normal state for every resolved visual frame, records every original rectangle before mutation, and rolls the entire set back if any move or exact rectangle verification fails. Provider guidance distinguishes real ambiguity from hosted aliases: when same-title rows contain exactly one application-specific process and the remaining rows are `ApplicationFrameHost.exe`, the application-specific identity is selected and the adapter still performs local visual-frame normalization; distinct real application windows, such as separate browser profiles/windows, remain clarification-worthy. When hosted normalization has multiple candidate frames, single, pair, and set placement all use DWM cloaking only as a conservative ambiguity tie-break: exactly one `DWM_CLOAKED=0` frame is accepted; zero or multiple uncloaked frames remain blocked. DWM cloaking is not a general eligibility rule.

Visible-window restore is intentionally narrow. `restore_window` accepts only the exact PID, bounded title, and opaque `target_token` produced by `window_snapshot`. THE OS revalidates that requested identity before any hosted normalization, blocks LYRA's own resolved window, uses `SW_RESTORE` on the resolved visual frame when minimized or maximized, and verifies with `IsIconic` and `IsZoomed` that the result is normal. Raw window handles remain local. The action is `NORMAL`: it does not close the window, terminate a process, type input, or inspect window contents.

Visible-window maximization is intentionally narrow. `maximize_window` accepts only the exact PID, bounded title, and opaque `target_token` produced by `window_snapshot`. THE OS revalidates the requested identity before any hosted normalization, blocks LYRA's own resolved window, asks Windows to maximize the resolved visual frame with `SW_MAXIMIZE`, and verifies that resolved frame with `IsZoomed` before reporting success. Raw window handles remain local. The action is `NORMAL`: it does not close the window, terminate a process, type input, or inspect window contents.

Visible-window minimization is intentionally narrow. `minimize_window` accepts only the exact PID, bounded title, and opaque `target_token` produced by `window_snapshot`. THE OS revalidates the requested identity before any hosted normalization, blocks LYRA's own resolved window, asks Windows to minimize the resolved visual frame with `SW_MINIMIZE`, and verifies that resolved frame with `IsIconic` before reporting success. Raw window handles remain local. The action is `NORMAL`: it does not close the window, terminate a process, type input, or inspect window contents.

Graceful visible-window close is confirmation-gated. `close_window` accepts only the exact PID, bounded title, and opaque `target_token` produced by `window_snapshot`, and is classified `DESTRUCTIVE` because closing an application window can affect unsaved work. Its preview is static and carries a PID/title/token execution guard. After approval, THE OS preserves the stale-token/title-change checks on that requested identity, may normalize a hosted CoreWindow alias only after exact identity succeeds, blocks LYRA's own resolved window, sends only normal `WM_SYSCOMMAND/SC_CLOSE` to the resolved visual frame, and waits up to 3 seconds for that frame to be destroyed or become non-visible. Raw window handles stay local. It never escalates to process termination or force-kill; if an application keeps the window open for its own save/confirmation UI, THE OS reports that closure was not verified.

Path mutation is intentionally bounded. `create_directory` creates only one level and never creates missing parent directories. `move_path` refuses existing destinations and blocks moving protected Windows system sources or moving a directory inside itself. `trash_path` uses the Windows Recycle Bin rather than permanent deletion, refuses protected system paths, and verifies that the original path disappeared after the shell operation. Mutation previews carry local path/signature guards so a changed source is blocked before execution.

`open_path` verifies that the target exists before handing it to the Windows shell. For generic files and folders, THE OS can verify the local target and that the shell-open request was submitted, but it does not claim that the associated GUI rendered successfully. Live visual acceptance remains the final check for that handoff.

Task cancellation is cooperative. THE OS does not forcibly kill a provider HTTP request or a local action that is already in progress. Instead, cancellation is checked before provider work, before local side effects, after each verified action, and before the next step. Pause follows the same safe checkpoints.

For the OpenAI Responses adapter, tool calls are deliberately serial (`parallel_tool_calls: false`). THE OS executes at most one model-proposed action at a time, verifies it locally, returns its `function_call_output`, and only then allows the model to propose the next step.

The Responses adapter remains stateless with `store: false`. It replays response output items and tool results locally for continuation and requests encrypted reasoning items when tools are enabled.

The session context is intentionally separate from persistent memory. Normal conversation is not automatically written to SQLite.

## AI configuration

Create a local `.env` file when a provider is ready to be used:

```text
THEOS_AI_PROVIDER=openai
THEOS_AI_MODEL=<model-id>
THEOS_AI_API_KEY=<secret>
THEOS_AI_BASE_URL=https://api.openai.com/v1
```

The real `.env` is ignored by Git. Without AI configuration, LYRA keeps actions and memory working and reports that conversational AI is not configured.

For conversational context, THE OS re-sends a bounded set of recent visible turns and requests `store: false` from the Responses API. Persistent memory remains a separate explicit local feature.
